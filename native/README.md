# LocalCorrect for classic Outlook

Native experimental candidate: `1.0.0-rc.5`. Shared-core quality and local helper measurements are recorded below. The release links its exact passing Windows CI build and artifact digest; physical Outlook acceptance is still unverified. Native RC3 remains the fixed comparison release; native RC4 remains an earlier experimental release.

This is a native COM add-in for classic Outlook 2019, both 32-bit and 64-bit, on 64-bit Windows 10/11. A .NET Framework 4.8 COM proxy launches a separate x64 correction helper containing its own .NET 10 runtime, Jint 4.17.0, ONNX Runtime 1.31.1, dictionaries and local contextual model. 32-bit Windows is unsupported; 32-bit Office on 64-bit Windows is supported by this architecture. New Outlook, macOS and mobile are unsupported. It needs no Outlook web manifest, Microsoft account deployment, Exchange deployment, local server or hosted scripts.

## Install and use

Close Outlook. Run `LocalCorrect-Outlook-Setup.exe` as your regular Windows user. It installs under `%LOCALAPPDATA%\LocalCorrect\Outlook` and registers only LocalCorrect's COM class and Outlook add-in in HKCU. It does not require administrator privileges. The executable is unsigned. Office policies that require signed add-ins can block it; this installer does not change those policies.

Install Microsoft's latest supported **Visual C++ v14 Redistributable for x64** first, using the [official Microsoft download page](https://learn.microsoft.com/en-us/cpp/windows/latest-supported-vc-redist). The helper is x64 even when Office is 32-bit; the x86 runtime alone is insufficient. LocalCorrect setup checks the fixed machine-wide x64 runtime registry key and required DLLs in the Windows system directory before staging files or writing registration keys. Its toolset-family floor is 14.44, matching the pinned ONNX Runtime binary; the latest serviced v14 is recommended. Missing, unreadable or insufficient prerequisites stop setup with the Microsoft URL. This check does not prove every servicing build compatible. Helper startup still fails closed if its native dependencies cannot load. Microsoft's separate runtime installation may require administrator privileges. LocalCorrect does not download or install it.

Pop out the email compose window. Open the LocalCorrect ribbon tab. Select English or German in Settings. Select prose and choose **Correct selection / body**, or press Ctrl+Shift+L. With no selection it processes the body, up to 20,000 UTF-16 code units. Settings can change the shortcut to Ctrl+Shift or Ctrl+Alt plus a letter. If another application owns the shortcut, use the ribbon. Inline replies in the main Outlook window are not supported, use Pop Out.

Dictionaries and the model initialize in the helper in the background when the add-in loads, without reading any email. A first action waits if initialization is still running. Correction runs only when invoked. It never sends or saves mail, logs body text, monitors typing, or contacts a correction service. The hotkey is registered only while an eligible compose window is active and its Word body editor has keyboard focus. It does not act on the subject or address fields. A timer checks window eligibility, not typed content. English and German are explicit modes, with conservative correction as the default. Both saved modes currently share the same precision-first policy. Review the result before sending. Ctrl+Z should undo the correction as one action.

Only changed word ranges are replaced. Unchanged ranges and their formatting stay intact. Links, fields, content controls, the Outlook automatic-signature bookmark, code-like fonts, and engine-recognized quoted text are excluded. Arbitrary manually inserted signatures, unmarked code and unusual reply templates cannot always be recognized; select only the prose you intend to correct. Mixed formatting inside a changed word is not guaranteed to survive. Tracked and protected documents are refused. This is not a general rich-editor adapter.

The COM proxy runs on a serialized worker in its own .NET Framework AppDomain. It exchanges bounded, versioned UTF-8 JSON frames with the fixed bundled helper through inherited standard-input/output streams. There is no listening socket or HTTP service. The proxy validates original edit spans and reconstructed output, kills the helper on protocol faults/timeouts, and permits a new invocation to start it again. The helper exits when its parent exits. Outlook-wide assembly policy is unchanged. If the document, selection or foreground window changes during correction, the result is discarded. Selections cutting through a word, combining sequence, joined identifier or surrogate pair are refused. A host without Word custom Undo support is refused before edits. If an edit fails midway, the add-in attempts to undo the complete custom action. A failed correction is not automatically retried.

ONNX Runtime telemetry controls are set before helper process creation and repeated before runtime initialization. `ORT_DISABLE_TELEMETRY=1` handles the 1DS backend. The exact Windows NuGet 1.31.1 binary uses legacy ETW, so `ORT_RUNNING_UNIT_TESTS=1` suppresses provider registration through that version's internal guard. The code also calls `DisableTelemetryEvents`. This version-specific workaround must be rechecked when changing ONNX Runtime; it is not a universal opt-out guarantee for other binaries. Windows ETW behavior has not yet been traced on the final candidate. See [privacy](../PRIVACY.md).

Remove it through Windows Apps, or run the installer with `/uninstall`. Removal deletes only owned registration keys and unchanged files in its inventory. Language/shortcut preferences remain. Uninstall before installing another version; this candidate refuses to replace an actively registered installation. If removal retains modified or unrelated files, it keeps the ownership marker and inventory so removal can be retried. A later install verifies those records and moves the retained folder intact to a unique sibling named `Outlook.retained-...`, then installs into a fresh folder. The installer reports the retained folder location. Missing or invalid ownership records cause refusal without moving or removing files. An uninstaller launched from its installation folder copies itself to a uniquely named temporary executable so its installed copy can be removed.

## Build

Requirements: Node.js 22+, Python 3 and .NET SDK 10. Windows build/test hosts also need the system x64 VC runtime. NuGet packages are pinned and lockfiles are checked in. Microsoft reference assemblies permit compiling .NET Framework on Linux. Restore/build download dependencies; installed correction uses local files and the separately installed system VC runtime.

```sh
npm ci
node scripts/build-native.mjs --core /path/to/localcorrect-browser --dotnet /path/to/dotnet
```

Output: `dist/LocalCorrect-Outlook-Setup.exe`, a managed Windows PE executable with an embedded ZIP payload. The same AnyCPU proxy supports both Outlook bitnesses and launches the bundled self-contained `win-x64` helper. The installer writes COM registration in both registry views on 64-bit Windows. A separate .NET 10 installation is not required; .NET Framework 4.8 is still required for the proxy and installer.

Use `--release --locked` only with a clean core checkout matching `core-source.json`. The core tree hash, all corpus hashes, document counts and corresponding source are included in the payload. The parity build includes the original email corpus in both modes, the existing scale development, holdout and blind sets, the RC5 blind set and every additional corpus declared in `evaluation-freeze.json`. Missing required corpora or mismatched hashes stop the build. Release builds also require a frozen hash for each scale corpus. The payload carries the complete shared core, tests, generators, vendor data, licenses and candidate/protection/ambiguity/inflection provenance records. `--skip-tests` is for incremental compile checks, never a release gate. The installer carries native/core source, dictionaries and license notices plus the exact runtime NuGet packages. Jint runs without CLR interop. Dependency package metadata records license expressions and source repositories.

The contextual ONNX model is approximately 47 MB. It is fine-tuned from an MIT-licensed BERT Mini base. The corresponding browser source includes the model, tokenizer, training/export scripts, source provenance and notices. Raw learner text and private correspondence are not included in the installer source bundle.

The package excludes general VC runtime DLLs and the Microsoft redistributable installer. Only the self-contained .NET runtime's own licensed `vcruntime140_cor3.dll` is retained. The native build pins the ORT Windows DLL SHA-256 and records it with the prerequisite in `build-info.json`; changing that DLL requires reviewing the telemetry backend and runtime requirements again. See [third-party terms](../THIRD_PARTY.md).

## Runtime evidence

An earlier RC5 integration with the first encoder and an empty contextual acceptance policy measured 12.29 seconds of helper cold readiness on an Intel Core i5-1038NG7 under Linux. Warm approximately 1,000-word helper roundtrips measured 377–575 ms in English and 549–786 ms in German; peak helper working set was 611 MiB. These are integration measurements, not final RC5 benchmarks or Windows/Office timings. These earlier measurements are retained only as implementation history.

For comparison, the final native RC4 core measured about 11.6–12.0 seconds of initialization in the isolated Linux/.NET 10 development engine on the same CPU. Two 1,000-word stress fixtures measured first actions of 1.01–1.21 seconds, warm medians of 378–391 ms and peak whole-process RSS of about 455 MiB. These historical development-engine measurements do not establish RC5 performance or additional Outlook RAM.

## Final local helper measurement

With the final 47,246,299-byte encoder and 13-action policy, the isolated Linux helper on the same i5-1038NG7 measured 13.21 seconds of cold readiness and 610 MiB peak helper working set. Three approximately 1,000-word roundtrips took 581/416/388 ms in English and 641/453/366 ms in German. This includes anonymous-pipe exchange, shared Jint preprocessing/correction and two-thread CPU ONNX inference. It excludes the Outlook application's own memory and UI/COM overhead. These are development-machine measurements, not Windows or Office acceptance.

The actual rebuilt helper passed the neural-only have-to-has fixture, selected greeting-name preservation, joined-token rejection, restart after rejection, parent-exit cleanup and malformed-frame silent failure. Twenty-five tokenizer cases and 40 raw ONNX arithmetic probes matched the training fixtures within 0.0001, with maximum native error about 0.0000056. Full public-corpus parity and both Office-proxy bitnesses are checked by the Windows CI build referenced by the release.

The shared core retains zero unwanted edits on 6,200 synthetic documents in both modes. Its independently authored 200-case audit has nine wanted edits, zero unwanted edits and 107 misses, identical to the prior core. Two independent semantic reviews support 21 additional partial corrections on 3,200 real learner pairs; whole-document exactness remains 617/3,200. This is limited contextual coverage, not a general grammar model. See the [fixed RC6 quality report](https://github.com/mrksrus/localcorrect-browser/blob/v1.0.0-rc.6/QUALITY.md).

## Required acceptance before a tested Windows release

Linux compilation and engine tests do not prove Office COM loading. This candidate requires the following on actual Outlook 2019 x86 and x64:

- Install as a standard user, inspect registered keys, start Outlook and confirm the ribbon loads.
- Test English and German corrections, a selected passage and a whole body. Disconnect networking and repeat.
- Test HTML and plain-text mail, bold/italic text, emoji, tables, automatic signatures, quoted replies, hyperlinks, fields and attachments. Verify untouched text/formatting and attachments remain intact.
- Test Ctrl+Z produces one undo step and restores text and formatting. Induce a mid-edit failure and verify rollback.
- Edit or switch windows while correction is running and verify no stale change is applied. Verify read-only mail and inline replies are excluded.
- Change the shortcut, test a collision, switch away from Outlook and verify the shortcut is released. Use the ribbon when a shortcut is reserved.
- Test install refusal with Outlook open, an existing/conflicting install, a missing/old/x86-only VC runtime and restrictive Office policy. Verify prerequisite failures leave installation files and registration untouched. Uninstall with unrelated/modified files present and verify they remain; uninstall must still work if the VC prerequisite is later removed.

Actual Outlook acceptance remains unverified. The candidate may be published as an explicitly experimental prerelease with that limitation; do not describe it as a tested Windows/Office release until these checks pass. Source review, final quality/runtime checks, passing Windows CI and unchanged artifact promotion remain separate release checks.

The SDK build and portable engine tests are recorded separately. Native RC3 compared 5,522 document/mode cases against the JavaScript engine. RC4 discovered the pinned candidate's declared corpora and recorded exact per-corpus counts and total `parityCases` in `build-info.json`, including the browser RC5 blind set. RC5 retains this discovery and adds contextual tensor/protocol checks. Runtime parity does not establish correction quality; that is reported by the [shared-core evaluation and measurements](https://github.com/mrksrus/localcorrect-browser/blob/v1.0.0-rc.6/QUALITY.md) at the final pin in `core-source.json`. Earlier release results are not evidence for RC5. Windows CI is configured to execute both x86 and x64 .NET Framework 4.8 clients against the bundled x64 helper, plus helper protocol, parity and installer checks. Linux compiles the net48 add-in and runs the portable net10 engine/helper checks. Use the exact release-linked CI run for final-candidate results. Neither runner exercises Office COM integration.

Fixed native RC3 Linux x64 .NET10 engine measurements on an Intel Core i5-1038NG7 recorded 222–487 ms for a first 1,000-word email after initialization, with warm medians of 124–153 ms and 367–369 MiB peak RSS. Initialization took 5.21–5.58 seconds. These are engine measurements, not actual Outlook/COM application timings or a guarantee on every CPU. The companion browser repository publishes fixtures, exact hashes and full measurements. Hosted Windows CI reports its own runtime timings. Real 32-bit Outlook memory headroom and end-to-end latency remain device acceptance work.

## Text language

Settings selects English or German. Mixed-language vocabulary preserves recognized words from both languages and remains enabled when upgrading older settings. Disable it for selected-language-only spelling vocabulary. Both choices keep names, software terms, quotations and literal syntax protected. Language settings are copied into each correction before the worker starts. The helper receives the saved boolean through the local bounded protocol. This changes lexical policy; the contextual model weights and thresholds remain unchanged.

The native helper prepares both selected-language spelling tables during background startup, before reporting ready. This moves one-time table decoding out of the first correction after a scope change. Startup can take longer than the earlier mixed-only helper; warm edits reuse the prepared immutable tables and do not retain document text.
